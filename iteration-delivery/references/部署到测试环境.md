# 部署到测试环境

本文件是 `iteration-delivery` **阶段 7 的子流程正文**，不是独立 skill。把一次迭代的代码合入 `env_test`、推到远端、再部署到测试环境服务器。

**这是对测试环境的真实变更**：服务器上会执行 Maven 打包、备份并覆盖运行中的 jar、`kill -9` 占用 8080 的进程、重启服务。整个过程测试环境不可用，耗时以分钟计。

`<repo-root>` 指 `git rev-parse --show-toplevel` 的结果。

## 环境事实

| 项 | 值 |
|---|---|
| 测试分支 | `env_test` |
| 服务器 | `root@120.25.50.247` |
| 服务器项目路径 | `/opt/PanEasyPush` |
| 部署脚本 | `<repo-root>/deploy_dev.sh`（**已被 git 跟踪**，服务器 `git pull` 后即为最新） |
| 运行 jar | `/www/wwwroot/pyt/java/tb-admin.jar`，同目录留有 `.bak` 备份 |
| JDK | `/www/server/java/jdk-11.0.19` |
| 服务端口 | 8080 |
| 日志目录 | `/www/wwwroot/pyt/java/logs` |
| 启动 profile | `local` |

核验方式与分支现状见 `部署环境与故障处理.md`。

`deploy_dev.sh` 的动作顺序：`cd /opt/PanEasyPush` → 打印当前分支 → **`read -p` 等一个 `y`** → `git pull` → `./mvnw package -DskipTests -q` → 备份现有 jar 为 `.bak` → 复制新 jar → `kill -9` 8080 端口进程 → `nohup java -jar` 启动。

三个必须知道的事实：

- **脚本自带 `-DskipTests`**：服务器端不跑测试。测试必须在本地全量跑过（阶段 5）；本流程不因此免除本地测试，也不改写脚本。
- **脚本自带一次 `git pull`**：本流程在跑脚本前会先显式 pull 并检查结果，脚本内那次是幂等的重复，不是重复部署。
- **推送到远端不会触发部署**：`core.hooksPath` 未设置，`my-hooks/pre-push` 虽存在但不生效；`my-hooks/post-push` 不是 git 的合法 hook 类型，永不执行。部署**只能**靠本流程的 ssh 步骤完成，不要以为 push 完就自动上线了。

## 授权边界

收到阶段 7 的确认凭据，即授权：在本地 `env_test` 上执行 merge、推送到 `origin/env_test`、ssh 登录 `root@120.25.50.247`、在 `/opt/PanEasyPush` 执行 `git pull` 与 `deploy_dev.sh`。

**不授权**（需用户当次明确同意）：`git push --force` / `--force-with-lease` / `--delete`；改写远端历史或删除远端分支；`git reset --hard`；修改服务器或仓库的配置文件（含 `application-local.yml`）；修改 remote URL、git 配置、hook 或 `core.hooksPath`；在服务器上执行与本次部署无关的命令。

## 前置条件

1. **确认凭据**：阶段 7 产生的用户确认原话摘要 + 时间。**没有凭据不得执行**。
2. **工作区相关改动已 commit**，并记录起始分支与 HEAD SHA（`git rev-parse --abbrev-ref HEAD`、`git rev-parse HEAD`）。
3. **明确迭代分支名**（默认当前分支）与远端（默认 `origin`）。

## 阶段 1：核对起点（只读，不停）

```bash
git fetch origin
git rev-parse --abbrev-ref HEAD
git rev-parse HEAD
git status --porcelain
git rev-parse --verify --quiet origin/env_test   # 远端是否已有 env_test
git rev-parse --verify --quiet env_test          # 本地是否已有 env_test
git rev-parse origin/dev                         # 本次要合入的主干
```

先向用户报告一行结论（起始分支、迭代分支、`origin/env_test` 存在与否、将合入的 `origin/dev` SHA），再继续。远端没有 `env_test` 属正常，阶段 3 会由 `git push -u` 首次创建。

## 阶段 2：本地合并到 env_test

```bash
git checkout env_test          # 本地不存在时改为：git checkout -b env_test origin/dev
git merge origin/dev           # 第一步：先与主干同步
git merge <迭代分支>            # 第二步：叠加本次迭代
```

两步都必须是 **merge，不是 rebase**，不在 `env_test` 上 force 任何东西。

**冲突一律停下**，不做补救动作：报告冲突文件清单、双方差异摘要，给出选项（用户解决 / `git merge --abort` 回到执行前）。**不自行 `--abort`、不自行选 `ours` / `theirs`、不跳过冲突**。

任一步失败后不得继续到阶段 3。

## 阶段 3：推送 env_test

```bash
git push -u origin env_test
```

首次推送用 `-u` 建立跟踪关系；远端已存在时 `-u` 也无副作用。

被拒时**停下报告**，不做补救：non-fast-forward → 报告本地/远端 SHA 与差异提交，**不 rebase、不 force**；认证失败 → 报告远端地址与凭据类型，**不改 remote**。

推送后报告：远端、分支、commit SHA、以及"本次推送未触发任何部署"这一事实。

**只推送、不部署的情形**：用户明确说"只要推送""先别部署"时，执行到本阶段结束即可，报告"代码已推送到 `origin/env_test`，**未部署**"，并说明部署需另行执行阶段 4。此情形下不进行任何 ssh 操作。

## 阶段 4：服务器部署

先探活，避免在连不通时反复重试：

```bash
ssh -o BatchMode=yes -o ConnectTimeout=10 root@120.25.50.247 'echo ok'
```

连不通 → 停下报告（`BatchMode` 会禁用密码提示）。可提示用户候选密钥 `my-hooks/root.pem`，但**由用户确认用哪个**，不自行轮试密钥。

连通后按顺序执行，**每条都要看输出和退出码**：

```bash
# 1. 确认服务器上的分支就是 env_test，不是别的
ssh root@120.25.50.247 'cd /opt/PanEasyPush && git rev-parse --abbrev-ref HEAD && git status --porcelain'

# 2. 确认 upstream，再拉取
ssh root@120.25.50.247 'cd /opt/PanEasyPush && git rev-parse --abbrev-ref HEAD@{upstream}'
ssh root@120.25.50.247 'cd /opt/PanEasyPush && git pull'

# 3. 执行启动脚本（脚本内有 read -p，用管道喂 y）
ssh root@120.25.50.247 'cd /opt/PanEasyPush && printf "y\n" | bash deploy_dev.sh'
```

分支不是 `env_test`、工作区有未提交改动、无 upstream、`git pull` 失败 → **一律停下报告**，不擅自 `checkout`、不 `reset`、不代建 upstream。

**第 3 条给足超时（≥10 分钟）**，服务器上要跑完整的 Maven 打包。

## 阶段 5：验证与报告

```bash
ssh root@120.25.50.247 'ls -l --time-style=long-iso /www/wwwroot/pyt/java/tb-admin.jar /www/wwwroot/pyt/java/tb-admin.jar.bak'
ssh root@120.25.50.247 'cd /opt/PanEasyPush && git rev-parse HEAD'
ssh root@120.25.50.247 'ss -lntp 2>/dev/null | grep :8080 || netstat -lntp 2>/dev/null | grep :8080'
ssh root@120.25.50.247 'tail -n 50 /www/wwwroot/pyt/java/logs/sys-info.log'
```

三条证据都要看：jar 时间戳已更新、服务器 HEAD 等于阶段 3 推上去的 SHA、8080 在监听。**用 `tail -n`，不要 `tail -f`**（会阻塞）。

报告必须区分三种状态，不得混为一谈：

- **代码已推送到远端**（`origin/env_test` 的 SHA）
- **服务器已拉取并部署**（服务器 HEAD、jar 时间戳、端口状态）
- **业务是否可用**——本流程没有接口冒烟测试，端口监听不等于业务正常。没有实际验证就不要说"验证通过"。

**启动失败或端口没起来**：如实报告 `deploy_dev.sh` 的输出与日志尾部，给出回滚步骤（见 `部署环境与故障处理.md`），**由用户决定是否回滚**，不自行执行。

## 失败与恢复

| 情况 | 动作 |
|---|---|
| 阶段 2 merge 冲突 | 停。报告冲突清单，给"用户解决 / `git merge --abort`"选项 |
| 阶段 3 push 被拒 | 停。报告 SHA 与差异，**不 rebase、不 force** |
| 阶段 4 ssh 不通 | 停。报告连通性错误，请用户确认密钥或网络 |
| 阶段 4 服务器分支不对 | 停。报告实际分支与工作区状态，请用户决定 |
| 阶段 4 `git pull` 失败 | 停。报告原始报错，不跑 `deploy_dev.sh` |
| 阶段 4 `deploy_dev.sh` 非零退出 | 停。报告脚本输出与日志尾部，给回滚步骤 |
| 阶段 5 端口未监听 | 停。报告日志尾部，给回滚步骤 |

详细的环境事实、hook 现状与回滚命令见 `部署环境与故障处理.md`。

## 收尾

完成后默认**切回起始分支**（起始分支就是 `env_test` 时不动），并在报告中说明当前所在分支。若因工作区有改动无法切回，停下报告，不强制切换。

## 红线

- 禁止 `git push --force`、`--force-with-lease`、`--delete`
- 禁止改写远端历史、删除远端分支
- 禁止在服务器上 `git reset --hard`、`git checkout -f`、改配置文件
- 禁止修改 `core.hooksPath`、hook 脚本、remote URL、`.gitignore`
- 未经用户明确选择，禁止使用 `--no-verify`
- 禁止把"推送成功"说成"部署成功"，禁止把"端口在监听"说成"业务验证通过"
