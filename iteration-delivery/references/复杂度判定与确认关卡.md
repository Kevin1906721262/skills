# 复杂度判定与确认关卡

复杂度决定本次迭代停几次确认。判定必须给出**证据**（具体文件、表、接口、模块名），不接受"感觉比较大"。

## 硬信号（命中任一 → 较大改动）

| 编号 | 信号 | 必须能指出的证据 |
|---|---|---|
| A1 | DDL、索引、历史数据迁移、回填、一次性初始化 | 具体表名、字段、SQL 文件或迁移步骤 |
| A2 | 金额、税率、分红比例、结算或统计口径变化 | 具体字段、公式或接口返回项 |
| A3 | 状态流转、权限、数据归属、事务或幂等语义变化 | 具体状态机、权限点或事务边界 |
| A4 | 接口契约变化（路径、必填性、错误码、枚举、空值序列化）或跨端交付 | 具体接口与消费端（PYT-web / PYT-h52） |
| A5 | 跨模块（≥2 个 reactor 模块）或跨仓库 | 模块名列表 |

## 计数信号（无硬信号时，命中 ≥3 → 较大改动）

| 编号 | 信号 | 必须能指出的证据 |
|---|---|---|
| B1 | 预计改动 Java 文件 ≥5（含新增） | 文件路径清单 |
| B2 | 业务入口 ≥3（Controller 方法、定时任务、管理接口） | 入口清单 |
| B3 | Mapper XML 或 Mapper 方法改动 ≥3 处 | 方法清单 |
| B4 | 新增或修改测试类 ≥3 | 类名清单 |
| B5 | 需求输入包含 PRD 或 HTML 原型 | 文件路径 |

## 判定规则

1. 命中任一 A → **较大**。
2. 无 A 命中且 B 命中 ≥3 → **较大**。
3. 其余 → **小**。

对 `tb-common`、`tb-framework` 这类基础模块的改动，A5 会高频命中——这是刻意的保守设计，基础模块影响面天然大。

## 判定时机

- **阶段 1 完成时初判**，写入 `.task/<迭代>/迭代说明.md` 的复杂度判定表。
- **阶段 2 完成后复核一次**——方案往往暴露更多改动点。
- **只允许"小 → 大"升级**：发现新硬信号立即升级，在下一个关卡报告，**不回溯补停，也不降级**。

## 用户覆盖

用户可在关卡①显式覆盖判定口径（例如"只要 B ≥3 才算大"）。覆盖写入 `迭代说明.md` 的"用户覆盖"行，**后续一律遵从，不再重复询问**。

## 关卡映射

| 判定 | 确认关卡 |
|---|---|
| 较大 | 3 次：阶段 1 后（关卡①）、阶段 2 后（关卡②）、阶段 7 前（关卡③） |
| 小 | 1 次：阶段 7 前（关卡③） |

中间阶段（3、4、5、6）**一律连续执行不停**。

## 关卡话术模板

```
--- 确认关卡 <n>/<total>：<阶段名> ---
迭代：.task/<迭代>/   分支：codex/<slug>

<3~5 条要点，每条一行，带具体文件/表/接口名>

待裁定：<只列真正需要用户拍板的点；没有就写「无」>

下一步：回复「确认」我继续阶段 <n+1>；回复修改意见我按意见调整后重新提交本关卡。
```

- 关卡①②是"呈报 + 等确认"。
- 关卡③（推送与部署前）额外必须展示：**待提交文件清单、commit message、合并路径（`origin/dev` + 迭代分支 → `env_test`）、目标远端与分支、部署目标服务器、影响面（测试环境在打包与重启期间不可用）**。确认后产出"确认凭据"（用户原话摘要 + 时间），供 `部署到测试环境.md` 子流程使用；无凭据不得推送或部署。
- 关卡③的确认**同时授权推送与测试环境部署**，不再单独设部署关卡。用户答"先别推"即整体停下，保留未提交改动。

## 与"澄清提问"的边界

两件事，不要混：

- **澄清提问**：业务缺口必需，可发生在任何阶段（含阶段 3~6 中途），一次提 1~3 个最关键问题。**不算审批**。
- **确认关卡**：流程决策点，只在阶段 1、2、7 的末尾，按复杂度决定次数。

关卡记录方式：在 `迭代说明.md` 的"确认关卡记录"表追加一行（关卡序号 / 阶段 / 时间 / 用户原话摘要 / 结论），并注明"确认记录是过程留痕，不是审批状态"。
