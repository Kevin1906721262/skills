# 踩坑总结

会话临近结束、或你主动要求复盘时手动触发。目标有两件事：

1. 把这次会话踩的坑**讲清楚**（自由叙述，不套模板）；
2. 把**可复用**的教训**沉淀成 skill**，让它在以后同类任务中自动生效，避免重蹈覆辙。

## 工作流程

### 第一步：回顾会话，识别踩坑点

回看当前会话的完整历史（对话、工具调用、报错、重试、修正），挑出这些信号：

- 报错 / 异常信息，以及当时的排查路径
- 走了弯路的尝试（先用了错误方案，后改对）
- 被纠正的误解或错误假设
- 配置、环境、API 的隐性陷阱（文档没写清、默认值坑人、版本差异）
- 反复出现的同一类错误

一次性、不会再遇到的琐事不算「坑」。

### 第二步：自由叙述地总结

不套固定字段，用自然语言把每个坑讲清楚，至少覆盖：

- 当时发生了什么（现象 / 报错）
- 根因是什么
- 最终怎么解决的（或正确做法）
- 一句话提醒：下次怎么一眼避开

按主题或时间线组织，宁短勿长。

### 第三步：沉淀成 skill（先征得同意）

先看第二步总结里**有没有值得沉淀的坑**：

- **没有踩坑、或没有值得沉淀的坑** → 跳过本步骤，**不提问**，直接进汇报。
- **有值得沉淀的坑** → **先问用户**，不要自作主张：

  > 这次有 N 类坑值得沉淀：……。要不要把它们写入已有 skill / 新建 skill？

  用户同意后再继续；拒绝则跳过本步骤。

用户同意后，对每一类坑执行：

1. **先找现成的**——搜索是否已有相关 skill 覆盖这类经验：
   - 查本地 `~/.agents/skills/` 是否已有
   - `npx skills find <关键词>`，或查 https://skills.sh/
   - **已有** → 征询用户后把经验**写入 / 引用**到该 skill，不重复造轮子；同时检查该 skill 的 `description` 是否已覆盖这次的新触发场景，没覆盖就一并补上，否则下次同类问题仍不会自动带出它

2. **没有则新建**——把踩坑总结出的「正确做法 / 检查清单 / 避免清单」固化成一个新 skill：
   - 位置：`~/.agents/skills/<name>/SKILL.md`
   - frontmatter 写清楚 `name`、`description`
   - **`description` 是"下次自动触发"的命门**——它决定模型下次遇到同类问题时会不会自动带出这个 skill。写法：
     - 写"**何时用**"，而不是"是什么"。例如「当…时使用」「遇到…报错 / 场景时使用」「用 X 技术做 Y 任务前必读」
     - 覆盖用户在真实请求里会用的**原话措辞**：工具名、报错关键词、任务类型、技术栈名——把这些词织进 description
     - 一个 skill 只聚焦一类坑；主题越散，description 越难写精准，越难被触发
   - 沉淀"避坑 / 经验"类 skill 时**默认自动调用**（不加 `disable-model-invocation`），这样下次同类任务才能被模型自动带出；`disable-model-invocation: true` 只留给像 evolve 这种需要用户手动 / 交互式发起的工作流
   - 正文就是这次踩坑结晶出的可执行经验（怎么做、别做什么）
   - 创建后告诉用户：skill 名、description 里埋了哪些触发词、何时会自动生效

### 第四步：汇报

总结输出后，列出：

- 本次踩坑清单（自由叙述）
- 已沉淀 / 新建的 skill（若有）
- 建议引用的现成 skill（若有）

## 原则

- **自由叙述**，不套模板。
- 只沉淀**可复用**的经验；一次性琐事只总结、不固化成 skill。
- **沉淀前先征得用户同意**，不自行写入或新建；没有踩坑则直接跳过、不提问。
- **创建 skill 前必须先搜**，避免重复造轮子。
- **`description` 决定"下次会不会自动触发"**——每个新 skill 的 description 都要埋入用户下次会说的关键词；这是"避免踩坑"落地的关键一环，不能只写一段笼统简介。
- 除非用户另有指定，新 skill 一律放在 `~/.agents/skills/`。
