# 反爬风控接口逆向 —— 踩坑结晶

针对「抓包 → 纯代码重放」会撞上的风控机制(以 MyH5Guard / 美团系 `mygsig`+`env-rp` 为例,规律通用)。

## 核心结论

1. **签名由前端 SDK 现生成,但重放是否被拦取决于场次严度,不是绝对。** 签名(如 `mygsig`)由 SDK 在浏览器运行时现生成,带 m0 时间戳并绑定请求上下文。对**严场次** urllib 重放会被拦(`240021002 網絡不穩定`);但对**宽松场次**,用模板头重放也能成功——服务器校验签名结构+指纹状态,**不校验 m0 新鲜度**(实测 15 小时前的签名照常下单成功)。所以重放失败要分场次看,别一口咬定"重放必死"。
2. **body 里的"指纹"字段可复用**(如 `cartRiskRequest.fingerprint`),不敏感;敏感的是头里的签名(`mygsig`)。——但见「指纹自洽性」: 指纹要与 env-rp **同源**,否则严场次被拒。
3. **正解:在浏览器页面上下文里用 `page.evaluate` 的 fetch 直接调接口。** 页面加载后 SDK 已注入,自动附加新鲜 `mygsig`(m0=当前时间),脚本只控制请求体和路径。实测 200 建单成功。
4. **严场次被 500 拦,优先怀疑「指纹不自洽」,不是设备被拉黑。** 见「指纹自洽性」。

## 诊断路径(按此顺序)

1. **先判断场次开售状态**(`saleStatus`),别先怀疑签名/指纹/风控。见「开售/未开售判断」。
2. 开售确认后重放被拒 → 做对照测试:同一张请求,一次 urllib 重放、一次 `page.evaluate` fetch。后者 200、前者被拦 → 用页面内 fetch。
3. 页面内 fetch 也报 500 → 查**指纹自洽性**(见下)。

## 开售/未开售判断(saleStatus)

- **信号**: 调 `/api/oversea/show/list?projectId=X`,看 `data[0].saleStatus`:
  - `3` = 开售中(可下单)
  - `1` = 未开售(页面 `ticket?pId=X` 会**重定向到 `detail?pId=X`**)
  - 其余枚举值语义未确认,一律当不可下单处理。
- **旁证**: 加载 `ticket?pId=X` 后看最终 `page.url`——跳转到 `/detail` 即未开售;停在 `/ticket` 为开售中。
- **注意**: `saleStatus` 是**场次级**(在 show 对象里),多场次演出要逐个判断,别拿 `data[0]` 代表全场。
- **位置**: 判断要放在 addToCart **之前**,未开售直接跳过该行,省掉后面的票档查询和下单请求。
- 未开售时下单会被 500 类文案拦截(「當前購票人數過多」等伪装),所以**先查 saleStatus,再谈风控**。

## 指纹自洽性(严场次的真正闸门,替代旧的"设备级冷却"结论)

- **现象**: 同一账号、同 IP,手动浏览器下单正常;脚本(页面内 fetch)全被 500「當前購票人數過多」拦。曾误判为"设备级冷却/场次级风控"。
- **真相**(实验验证): 严场次校验 **`env-rp`(环境数据)与 `cartRiskRequest.fingerprint`(声明的设备指纹)是否同源自洽**:
  - 旧脚本: `env-rp` = 当前脚本 Chrome 现算(新鲜), `cartRiskRequest.fingerprint` = 模板里**另一台设备/另一会话**抓的固定值 → **不一致** → 500。
  - 真实浏览器: 两者都出自真机 → 自洽 → 200。
  - **换全新会话自洽指纹**(新 profile 现抓 env-rp + 同会话现抓 fingerprint)→ **200 成功**。
- **宽松场次**(如 3863/3864): 不自洽也放行;严场次(热门/紧俏)才查。
- **判定**: 页面内 fetch + 模板旧指纹被拒,换成"同会话现抓指纹"就过 → 指纹自洽性问题,不是设备被拉黑、也不是 IP/账号被标记。
- **应对**: 每次下单用**本会话自己现抓的 `cartRiskRequest`**(env-rp 与 fingerprint 同源),不要用模板那份跨设备/跨会话的固定指纹。
- **别做**: 把真实设备的指纹和别的环境拼在一起发,会被当"分裂请求";自洽问题未解决前反复重试,只会延长冷却。

## 通用提醒

- 单账号常只有**一张待支付购物车/订单**:重复下单前先查 `pendingPay` 并取消旧的,否则报 `40010004`。
- 风控报错文案不可信:`當前購票人數過多`(500)、`網絡不穩定`(240021002)都可能是伪装;先按诊断路径定位真因。
- 测试节奏克制,一次只验证一个变量;被打进冷却后先停手。

## 最小可行代码(Playwright + CDP)

```python
def api_in_page(page, path, post=None):
    return page.evaluate("""async ({path, post}) => {
      const opt = {method: post !== null ? 'POST' : 'GET',
                   headers: {'Content-Type': 'application/json;charset=UTF-8'}};
      if (post !== null) opt.body = JSON.stringify(post);
      const r = await fetch(path, opt);
      return await r.json();
    }""", {"path": path, "post": post})
# 页面先导航到同源页面(让 SDK 加载), 之后所有带风控的接口都用它调
```
